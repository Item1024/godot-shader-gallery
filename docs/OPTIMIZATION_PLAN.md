## 4. 具体技术方案

### 4.1 生成与维护

修改 `tools/build_library.py`，新增 `tools/effect_profiles.py` 保存首批参数定义。`tools/effect_catalog.py` 继续负责分类和顺序，`tools/plain_language.py` 继续负责大白话说明。

生成器增加三个明确操作：

```text
python tools/build_library.py --check
python tools/build_library.py --effect dissolve/noise
python tools/build_library.py
```

- `--check` 在临时目录生成并比较，报告哪些受管理文件变化，不修改工作区；不一致返回非零。
- `--effect` 只更新该效果的生成文件及确实需要同步的总索引，不重写其余效果。
- 无参数全量生成继续保留；写入前执行相同的手改检查。
- 将已生成文件的内容哈希存入版本控制中的 `tools/generated_manifest.json`。当前内容与上次生成哈希不符时，停止覆盖并列出文件，要求先把修改合回生成源。
- 首次建立清单时先核对基线提交和一次临时生成结果。不能把用户手改文件直接当成新生成结果登记。
- 不提供静默强行覆盖路径。`docs/OPTIMIZATION_PLAN.md`、验证记录和人工确认的参考图均不属于生成文件。
- `assets/cottage.png` 已在仓库中，正常生成直接使用它。重新渲染小屋是另外的素材制作操作，不能成为全库重建的前提。
- 新增中性 LUT 时一并记录生成方式；所有演示与测试素材均在仓库内。

### 4.2 连续播放时间

新增小型 `shared/effect_player.gd`，负责一个或多个 ShaderMaterial 的时间，图库和独立接入示例共用。高斯模糊有两个材质，因此允许材质数组；不增加通用插件系统。

播放器遵守以下规则：

```text
没有暂停时：effect_time += delta * playback_speed
传入 Shader：u_time = effect_time，u_speed = 1.0
改速度时：只改下一段时间的累加速度，不重算 effect_time
速度为 0：停在当前状态
暂停时：时间保持，调参数和转相机仍可刷新画面
重置：时间归零，恢复当前效果自己的默认参数，清除尚未结束的触发事件
```

这是对现有 `u_time * u_speed` Shader 的兼容办法，避免时间被乘两次；现有直接使用 `u_time` 的进阶案例也使用同一时间。图库里的“播放速度”绑定播放器，不再直接改材质 `u_speed`。

播放器提供 `seek(seconds)` 供固定时间截图和事件检查使用；跳到指定时刻属于显式操作，不等同于改速度。单次受击记录 `u_event_time`，未触发时为 -1；Shader 根据 `u_time - u_event_time` 计算事件年龄，超时停止显示。

独立使用动态材质时附带播放器；单独拖入 `.tres` 只能得到静态状态，这一点在接入文档中写明。需要独立动画状态的物体使用独立材质实例。

### 4.3 点击和拖动

在 `shared/stage.gd` 中保留对实际展示网格的引用，处理三种明确的输入：二维图片位置、水面命中、护盾球面命中。

1. `SubViewportContainer` 的点击位置先按实际预览尺寸换成 SubViewport 像素位置，不能使用固定 900×660 作为输入换算尺寸。
2. 三维场景使用 `Camera3D.project_ray_origin()` 和 `project_ray_normal()` 得到世界射线，再变换到目标网格的局部空间。
3. 水面用本地波面高度函数求交。先用静止平面交点作初值，再按与 Shader 相同的波面函数迭代修正，最多 8 次、局部高度残差目标不超过 0.001 场景单位。只接受在网格宽深范围内、位于相机前方的解。过于平行、越界或不收敛时不触发。
4. CPU 与 Shader 的波面公式和参数需要成对更新，并由固定点测试检查；不能只求未变形平面的交点却声称精确命中起伏水面。
5. 护盾使用局部球面求交，取最近的正向交点。波纹使用表面点与命中点之间的球面弧长，避免拿屏幕坐标直接减模型坐标。
6. 按下并释放，移动不超过 4 个界面像素时触发点击；超过后只旋转相机，不同时触发受击。滚轮只负责缩放。
7. 本轮不为任意自定义模型建立通用碰撞系统。使用其他网格时，需要提供其命中求解方法，并在接入说明中注明。

命中验收：3 个相机方位 × 5 个有效表面点 × 2 个视口尺寸，水面和护盾各测 30 种情况。用已知表面点投影生成点击，再把响应中心投影回来，显示位置误差目标不超过 3 像素。另测点在模型外、拖动和窗口缩放。

API 依据：[Camera3D 射线与投影](https://docs.godotengine.org/en/4.7/classes/class_camera3d.html)。

### 4.4 参数面板

沿用现有三栏布局和配色。首批 20 项的 `metadata.json` 新增 `parameters` 数组，例如：

```json
{
  "parameters": [
    {
      "key": "u_amount",
      "label": "消失进度",
      "type": "float",
      "target": "material",
      "min": 0.0,
      "max": 1.0,
      "step": 0.01,
      "default": 0.32,
      "help": "0 完整显示，1 完全消失",
      "advanced": false
    }
  ]
}
```

- 首批只需要 float、bool、color、enum 和指定的 LUT 贴图选择。float 配滑块及可键盘编辑的数值框，enum 配下拉框。
- `target` 区分材质与播放器；`u_speed` 不作为专用材质滑块再次出现。
- 常用设置直接显示，次要设置收进“更多参数”；始终保留中文标签、单位、当前值、默认值及简短解释。
- 重置根据元数据默认值统一操作，不能把颜色一律重置成绿色，也不能依赖“滑块值变化信号一定会触发”。
- 控件变化时立即传入真实绑定对象。校验参数类型、范围和 uniform 是否存在；仅有声明不足以证明对画面有效，还要做参数变化的图像检查。
- 首批 20 项不出现无作用控件。其余 401 项暂时使用原有参数路径，并注明“基础参数”；不把这一轮完成等同于全库专用化完成。
- 搜索 0 结果时显示空状态并清除旧预览，避免列表为空却仍展示另一个效果。

交互原则参考本地 ui-ux-pro-max 技能的 `input-labels` 和 `progressive-disclosure` 内置规则。两次数据库搜索均未匹配到合适的参数面板条目，故采用内置规则，不引用无关搜索结果。实现仍使用 Godot 原生控件。

Uniform 范围和颜色类型依据：[Godot Shader uniform hints](https://docs.godotengine.org/en/4.7/tutorials/shaders/shader_reference/shading_language.html#uniform-hints)。

### 4.5 材质预设和接入场景

首批每个目录新增：

```text
material.tres         默认材质及参数
usage.tscn            使用 Sprite2D / MeshInstance3D / 后处理节点的最小接入场景
dependencies.json     需要随效果复制的 Shader、脚本和贴图
```

- 保留原来的 `demo.tscn`，继续作为图鉴展示入口；`usage.tscn` 不依赖图库的 catalog、侧栏或 `stage.gd`。
- 动态案例明确引用 `shared/effect_player.gd`；复制说明列出它，不能承诺只复制 Shader 就会自动播放。
- 高斯模糊多一个 `material_vertical.tres`。按“原图 → 横向模糊 → BackBufferCopy → 纵向模糊”组织场景，避免第二遍仍读取第一遍之前的画面。权重对称且总和为 1，0 半径直接还原。
- LUT 的包同时带暖色与中性颜色表；玻璃带可观察折射的背景与相机；水面带观察深度颜色所需的参考物。
- 复制验收按 `dependencies.json` 将必需文件复制到一个空白 Godot 工程，保持相对路径，导入后逐项运行 20 个 `usage.tscn`。此过程验证依赖闭合，不增加一键发布或插件安装功能。
- 每项 README 增加“拖到哪里、需要复制什么、如何用代码改值、动态效果如何播放、已验证平台”。保留大白话原理与实际局限。

双遍屏幕读取依据：[屏幕纹理复制与 BackBufferCopy](https://docs.godotengine.org/en/4.7/tutorials/shaders/screen-reading_shaders.html#behind-the-scenes)。

### 4.6 搜索和绘制开销

- 搜索输入合并等待设为 150 ms；新的输入覆盖旧请求。只对场景配置做短延迟，不能阻塞文字输入。
- 当前效果仍在结果中就保留选择、时间、相机和参数，不再反复 `_show()`；只有切换到另一个效果才搭建新预览。
- 首批元数据写明 `animated`。401 项未确认前按现有动态行为保守处理，不靠是否声明 `u_time` 猜测动画。
- 播放中的动态案例使用可见时更新；暂停或静态案例只在参数、尺寸、相机、选项、有效点击改变时请求一次重绘。
- 使用 `UPDATE_ONCE` 时等实际绘制完成后再截图，不能盲等两个绘制信号导致按需模式下的审查挂起。
- 未查看“实时演示”页时暂停预览时钟；返回后从原时刻继续，不跳过隐藏期间的动画时间。可见性与用户的暂停状态分别保存，返回预览不能擅自恢复已被用户暂停的动画。
- 按需停画前区分仍需逐帧变化的反射探针、雾等场景功能；未经验证的 401 项不直接套静态优化。

按需更新依据：[SubViewport 更新模式](https://docs.godotengine.org/en/4.7/classes/class_subviewport.html#enum-subviewport-updatemode)。

## 5. 验证方案与通过条件

### 5.1 结构和全库回归

扩展 `tools/validate.gd`：保留现有文件、Shader 和场景检查，增加首批参数的类型/范围/默认值检查、材质资源检查和依赖存在检查。

所有共享运行逻辑改变后，仍要跑完整 421 项 GPU 冒烟检查，且无新增脚本错误、Shader 编译错误或资源丢失。401 项没有因此获得像素级质量认证。

计划新增 `tools/test_runtime.gd`，检验有实际行为的逻辑：

- 正常播放 2 秒，改为 0.25 倍速后下一帧时间只增加 `delta × 0.25`；设置 0、暂停、恢复、重置均有确定结果。
- 改速度的瞬间 `effect_time` 不变；Shader 不再额外乘播放器速度。
- 默认参数直接写入绑定对象；同一个效果连续点两次重置也一致；两个独立材质的时间和颜色互不影响。
- 点击/拖动判定、空搜索状态、连续搜索不重建仍选中的效果。

### 5.2 20 项画面行为检查

新增 `tools/capture_visuals.gd`、`tools/compare_visuals.py` 和受版本控制的 `tests/visual_cases.json`。

每个效果固定 7 个状态，首批共 140 个参考状态：

1. 关闭效果。
2. 默认参数。
3. 主参数最小值。
4. 主参数最大值。
5. 一个次要参数的显著变化值。
6. 默认参数下的较早时间。
7. 默认参数下的较晚时间。

相机、输入素材、随机种子、曝光、画质和预览分辨率固定。常规参考时间为 1 秒，较早为 0.5 秒，较晚为 2 秒。单次触发效果在 manifest 单独定义：闪白的默认截图时间为 0.075 秒，受击波纹为 0.25 秒；另取触发前和超时后状态，不能在动画已经结束时误判“效果没有作用”。

- 每个案例在 manifest 中指定要比较的对象区域、参数、取值、是否预期随时间变化及特殊断言。
- 素材包含透明图案、纯色图、黑白硬边和颜色测试块，分别用于透明度、模糊与 LUT 检查。
- 溶解检查起点/终点；描边检查内外范围和透明度；进度控件检查空/满；高斯检查纯色不偏亮、硬边平滑；LUT 检查中性色表和边界颜色；点击交互另按第 4.3 节验收。
- 对默认截图独立运行两次，先确认同一环境的重复误差。初始目标：归一化 RGB 平均绝对差不超过 `1/255`，差值超过 `3/255` 的像素不多于比较区域的 0.1%；达不到时先定位不确定来源，不能直接放宽以掩盖问题。
- 对已人工确认的参考图，初始回归阈值设为平均绝对差不超过 `2/255`，差值超过 `8/255` 的像素比例不超过 1%。这些是同一环境内的检测门槛，不代表视觉质量评分。
- 有意改变效果的状态必须在指定区域产生可测差异，静态案例不同时间应保持一致；阈值由对应案例明确填写，不能给所有参数套同一条“必须变色”规则。
- 新参考图必须先检查并人工确认；禁止测试失败时自动把当前图覆盖为正确答案。不同显卡/驱动不直接复用自动判定结论。

参考图及 case manifest 放在 `tests/visual/` 并提交；实际输出、差异图和报告保留在已忽略的 `artifacts/`。现有 `_audit()` 的 PASS 名称在报告里明确为“运行检查通过”。

### 5.3 性能测量

先测当前基线，再用相同设置测改动结果。固定 Godot 版本、驱动、1440×900 窗口、900×660 的独立测试预览、同一画质，关闭垂直同步和帧率限制。正式记录同时写明实际渲染尺寸，不能只记窗口尺寸。

- 每个首批效果预热 120 帧，采样 600 帧，独立跑 3 次。
- 记录整帧 CPU 耗时、GPU 渲染耗时、预览内存、切换延迟及分辨率；具备逐帧数据时报告中位数和 P95。
- CPU 脚本与交互使用 Profiler / 明确计时；GPU 使用 Visual Profiler 或渲染时间戳。用 CPU 的一帧耗时冒充 GPU Shader 耗时不算有效数据。若导出方式拿不到某项，就标为未测并保留手工记录。
- GPU 效果开/关的整帧差只作为近似开销，并注明还包含绘制通路变化；不能声称是纯 Shader 内核耗时。
- 初始目标：预热后的首批效果切换 P95 不超过 150 ms；搜索文字处理不因 Shader 构建长时间阻塞；暂停并稳定后，受支持的预览在无交互的 120 帧内不重复绘制。
- 同设置下，未改算法的首批案例 GPU 帧时中位数如上升超过 `max(基线 × 10%, 0.2 ms)`，需要调查和说明。高斯从一遍改为两遍时先对比相近视觉质量，再讨论画质与耗时，不承诺精确算法一定更快。
- 不预填“60 FPS”或“提升百分之多少”；先记录实测，再为较重效果设置低、中、高画质的合理范围。

测量方法依据：[Godot Profiler 与 Visual Profiler 的范围](https://docs.godotengine.org/en/4.7/tutorials/scripting/debug/debugger_panel.html)。
